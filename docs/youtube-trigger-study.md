# YouTube の動画をパッドでトリガーする機能の検討（2026-09 / v0.3.137 時点）

「YouTube の動画をトリガー出来る機能」を、ブラウザ単体の楽器である MICS009 にどう載せられるかの検討。
**結論を先に**：音は **Tab Audio（既存）で取り込み**、映像は **IFrame で見せるだけ** のハイブリッドが現実的。
YouTube の音そのものをパッドで鳴らす（IFrame の seek を叩く）のは、遅延と iOS の制約で「演奏」にならない。

## 1. 「トリガー」の読み方（3通り）
| 読み方 | 何が起きるか | 音の道 |
|---|---|---|
| A. YouTube の音をパッドに**取り込む** | 動画の一部をサンプルにして、いつもどおり叩く | 既存（12bit/26kHz・SSM2044・P-LOCK・書き出し すべて乗る） |
| B. パッドで動画を**頭出しする**（キューポイント） | パッド=動画内の時刻。叩くとそこから再生（ビデオ・サンプラー） | YouTube プレイヤー直出し（ローファイ鎖に**乗らない**） |
| C. シーケンサーと**同期**して動画区間を鳴らす | STEP に動画区間を置き、ビートに合わせて再生 | 同上 |

## 2. ブラウザでできること・できないこと（前提）
- **YouTube の音声は Web Audio に取り出せない**。IFrame Player API はクロスオリジンで、`MediaElementSource` も `captureStream` も使えない。
  唯一の道は **タブ音声の共有（`getDisplayMedia`）＝既存の Tab Audio**。これは PC の Chrome/Edge だけ（**iOS Safari は不可**）
- **seek の反応は 100〜400ms**。バッファ済みでも 100ms 前後、未バッファは秒単位。指ドラムの許容（10〜20ms、`docs/ui-rules.md` のレイテンシ予算）を桁で超える。
  この環境（開発サンドボックス）から youtube.com に届かないため**実測はしていない**。実機で測る手順は §5
- **モバイルの自動再生規制**：iOS はユーザー操作ごとに `play()` が要る。パッドのタップは操作なので 1 回目は鳴るが、シーケンサーからの seek+play は止められる
- **複数プレイヤー同時**は不安定（音が重ならない＝ロールやレイヤーができない）。同じ動画の別区間でも 1 プレイヤーでは 1 音
- **ダウンロードして取り込む**（yt-dlp 的）はブラウザ単体では不可能で、利用規約にも反する。埋め込み（IFrame）は規約の範囲。
  埋め込み不可の動画（権利者設定）がある

## 3. 既にできること
- **Tab Audio**（録音パネル → Tab Audio）：別タブで YouTube を再生し、そのタブの音を共有して録る。今でもこの手順で YouTube から
  サンプルを作れる（PC のみ）。**ただし案内が無い**＝知っている人しか使えない（aki rule 違反）
- **GTR の同一オリジン iframe ＋ postMessage**（`70-sampling.js`）：全画面 iframe を出し、✕ と ESC で必ず脱出できる型がある。
  映像を出す枠はこれを流用できる

## 4. 案と評価
| 案 | 中身 | 良い | 悪い | 大きさ |
|---|---|---|---|---:|
| **①「YouTube から録る」導線** | 録音パネルの Tab Audio に「YouTube などのタブの音を録る」と手順（別タブで再生 → 共有でそのタブと「タブの音声を共有」にチェック）。PC でだけ出す。取り込み後は自動で EDIT（既存） | 既存の音の道にそのまま乗る。実装が小さい。規約も安全 | iOS では使えない（表示しない）。動画の「映像」は関係しない | 小 |
| ② VIDEO パッド（B 単体） | IFrame を情報窓か全画面に出し、パッド=キュー（`seekTo`+`playVideo`）。パッド長押しでいまの時刻をキューに | 「動画を叩く」見た目は新しい | 音がローファイ鎖に乗らない・書き出せない・P-LOCK 効かない。遅延 100〜400ms。1 音しか出ない。iOS で止まる。**演奏として成立しない** | 中 |
| **③ ハイブリッド（A＋映像）** | 音は ① で取り込む（`.mics` に入る＝いつもの音）。映像は IFrame で「見せるだけ」：パッドを叩いたら `seekTo(取り込み時の時刻)`。ズレは映像だけに出る（音は正確） | 音は本物。ライブで映像が付いてくる（VJ 的）。iOS でも音は鳴る（映像は追従しないだけ） | 取り込み時刻をパッドに覚えさせる仕組みが要る（Tab Audio 中に YouTube の時刻は取れない → 手入力 or 共有画面を見ながら「いま」ボタン）。IFrame の枠が画面予算を食う | 中〜大 |
| ④ C（同期） | STEP に動画区間 | — | ② の弱点をそのまま持ち、先読み（100ms）で seek を前倒ししても安定しない | 大 |

**推奨**：**① を先に**（次の小さな版で出せる。YouTube 由来のサンプルが「いつもの音」になる）。
**③ は PoC** として、実機で seek の遅延を測ってから（§5）。② と ④ は**やらない**（ドラムマシンの手触りを壊す）。

## 5. 実機で測ること（PoC の前に）
`tools/yt-probe.html` を置いた（公開物ではない）。IFrame Player API で `seekTo` → `PLAYING` になるまでの時間を 20 回測って中央値と最悪値を出す。
```sh
python3 -m http.server 8137   # リポジトリの根で
# PC:      http://localhost:8137/tools/yt-probe.html?v=<動画ID>
# iPhone:  http://<PCのLAN IP>:8137/tools/yt-probe.html?v=<動画ID>   （同じ Wi-Fi）
```
見るもの：中央値が **50ms を切るか**（切らないなら ③ でも映像の追従は「雰囲気」止まり）、iOS で 2 回目以降の `playVideo` が止められないか、
埋め込み不可の動画でどう出るか（`onError` 101/150）。

## 6. 決めてほしいこと（producer）
1. 「トリガー」は**音**か**映像**か（① だけで足りるか、③ の映像まで要るか）
2. iOS で使う場面があるか（Tab Audio は PC 限定。iOS は「PC で作った `.mics` を開く」運用になる）
3. 権利：取り込んだ音を含む `.mics` の共有（`73-share-export`）は私的利用の範囲を超えうる。共有時に注意書きを出すか
